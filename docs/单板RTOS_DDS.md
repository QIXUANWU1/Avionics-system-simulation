# 单块天脉 3 板里的 DDS

## 一、DDS 在哪一层

天脉 3 负责调度原生任务、容器和设备访问。DDS 是应用可采用的发布与订阅中间件，位于系统接口和应用之间。采集服务发布一种带类型的数据，订阅服务读取自己需要的类型与服务号。应用依旧负责数据年龄检查和业务计算。[OMG DDS 1.4](https://www.omg.org/spec/DDS/1.4/About-DDS)

一台 RTOS 里可以有原生任务和多个容器。A 板的原生大气采样与容器内的空速字编码就是本版的例子。两者都属于 A 板，虽然在 Linux 台架的配置中分在同一个工作域，目标板上的任务仍可通过本机 DDS 分开运行。

## 二、本版实现与边界

| 项目 | 本版做法 |
|---|---|
| 名单 | 根据五板配置与服务依赖生成 `rtos_local_inputs`。两端必须是同一块 RTOS 板上的目标服务。原生任务与容器均可在名单内。 |
| 发布 | `ima_rtos_dds_prepare` 检查发布服务的归属和本板是否有订阅者，再准备供 `imalab::State` 使用的字段。 |
| 接收 | `ima_rtos_dds_accept` 核对订阅关系、来源域、会话、序号和年龄。过期、重复或不属于本板的样本不更新接收值。新到的无效样本可以主动清除上一份有效读数。 |
| 状态消息 | 计划使用按服务编号分实例、深度 1、尽力而为、无历史持久化。周期刷新的是最新状态，消费者按服务规定的有效期决定是否使用。 |
| 平台工作 | SDK 适配负责本机参与者、发现范围、DDS 写读和本板单调时钟。C 检查层使用固定大小的结构，能先作为独立代码编译与测试。 |

本版实测范围是离线 C 代码。Linux 台架有 Cyclone DDS 通路。天脉 3 的 DDS SDK 绑定、参与者发现和时序留给上板集成。

## 三、板间关系怎么读

板间关系图描述谁需要谁的数据。例如 B 板的姿态选择会读取 C 板的备用惯性数据。这条边保存在应用依赖里，板间传输的协议、物理链路、时间同步、冗余和网关留待后续选定。板内适配器不会因为这条应用依赖存在就把它当成同板 DDS 订阅。
